# 项目完整架构与请求流程（源码核对版）

核对日期：2026-10-28。本文描述当前工作区源码中的实现；模型、数据库等具体后端由配置与组件加载结果决定。本文没有启动服务、调用远程模型或重新运行评测。

这是一组互相对应的架构图：总图回答“系统由什么组成”，请求图回答“一次请求怎样运行”，子系统图展开检索、工具与记忆。不同图中的同名模块是同一个组件，不是重复部署的服务。

建议先读第 1、3 节，再按简历涉及的内容阅读其余部分。实线表示图内的调用或处理方向；虚线表示辅助依赖、配置装配、可选接入或未来一轮请求，具体含义在边上标明。依赖图里的分叉不代表代码并行执行。

## 2. 启动装配：组件先被创建，请求才开始执行

```mermaid
flowchart TD
    A["ASGI app / FastAPI lifespan<br/>CLI 本进程模式也可直接构建容器"] --> B["Settings：环境变量与 .env<br/>API 模式另配置日志"]
    B --> C["build_container：按是否配置 LLM<br/>选择 DeepSeekProvider 或 OfflineLLMProvider"]
    C --> D["build_infrastructure<br/>按 database_url 创建引擎<br/>create_all 初始化表 → Session 工厂"]
    D --> E{"启动时 Redis 可连接？"}
    E -->|"是"| ER["Redis 缓存 + Redis 限流"]
    E -->|"未配置或连接失败"| EM["内存缓存 + 内存限流"]
    ER --> F["build_retrieval：选择 Embedding Provider"]
    EM --> F
    F --> G["每次容器构建执行 ingest_knowledge<br/>全量读取支持的知识文件"]
    G --> H["构建 BM25 与 Qdrant / 内存向量索引<br/>组装 HybridRetriever 与 DocumentReranker"]
    H --> I["注册 15 个内置工具<br/>按配置合并本地与远端适配工具"]
    I --> J["创建 ChatService<br/>创建节点依赖，build_graph 并 compile 一次"]
    J --> K["AppContainer 就绪<br/>API 模式保存到 app.state.container"]
    K --> L["接收多轮请求，复用组件与编译后的 Graph"]
```

- 数据库是硬依赖；没有“PostgreSQL 连接失败后自动切到 SQLite”的逻辑。
- LLM Provider 根据配置选择；不是先探测 DeepSeek API，探测失败再全局切换 Offline Provider。真实模型调用失败由各模块分别处理。
- 当前启动每次都执行 ingest，不存在通用的“检查索引版本后直接跳过知识重建”分支。
- Cross-Encoder 可在第一次需要时加载；容器创建完成不代表全部本地模型已经完成推理验证。
- `build_container(seed=False)` 默认不写演示数据。演示数据通过显式操作准备。

源码：`app/main.py`、`app/services/container.py`、`app/repositories/db.py`、`app/providers/embeddings.py`、`app/providers/reranker.py`。

## 3. 一次请求的完整主流程：包含全部 Graph 节点

```mermaid
flowchart TD
    U["用户 / Web / CLI 远程模式"] --> HTTP["HTTP 中间件<br/>trace_id 与 request_id"]
    HTTP --> API["FastAPI：请求 Schema 校验<br/>获取已构建的 AppContainer"]
    API --> LIMIT["ChatService：按 user_id 限流"]
    LIMIT --> SESSION["创建或复用 session_id<br/>打开请求作用域 DB Session"]
    SESSION --> CONF{"带 confirm_action_id？"}
    CONF -->|"无"| HIST["创建或获取会话，读取最近 20 条消息<br/>初始化 AgentState，summary 当前置为空"]
    CONF -->|"有"| VERIFY["查进程内待确认表<br/>校验存在性、有效期、用户和会话绑定"]
    VERIFY -->|"有效：恢复保存的动作参数"| HIST
    VERIFY -->|"无效"| INVALID["InvalidRequestError"]

    subgraph GRAPH["LangGraph：10 个节点；通过 AgentState 传递结果"]
        START(["START"]) --> GUARD["apply_guardrail<br/>检测提示词注入"]
        GUARD -->|"通过"| INTENT["classify_intent<br/>模型分类或规则回退 + 覆盖层纠偏"]
        GUARD -->|"拦截"| REF["refuse_answer<br/>生成固定拒答"]
        INTENT --> ROUTE["route_complexity<br/>模型判断或规则回退<br/>有效确认动作强制走 AGENT"]
        ROUTE -->|"DIRECT"| GEN["generate_answer<br/>普通生成 / 确认提示 / 缺参数提示 / 降级回答"]
        ROUTE -->|"SINGLE 或 MULTI"| RET["retrieve_docs<br/>普通检索或 SelfRAGLoop"]
        ROUTE -->|"AGENT"| PLAN["plan_tasks<br/>Skill、模型计划、计划约束、待确认提案"]
        ROUTE -->|"REFUSE"| REF
        RET --> GEN
        PLAN --> EXE["execute_tools<br/>待确认时跳过执行<br/>否则校验、幂等、执行、只读降级"]
        EXE --> GEN
        GEN --> FAITH["check_faithfulness<br/>按条件跳过，或检查、重写、兜底、拒答"]
        FAITH --> MEMORY["compact_memory<br/>加入本轮消息，估算预算，压缩或摘要"]
        REF --> MEMORY
        MEMORY --> ENDNODE(["END"])
    end

    HIST --> START
    ENDNODE --> RESP["ChatService：将最终状态转为 ChatResponse"]
    RESP --> SAVE["追加本轮用户与助手消息<br/>保存非空摘要 → 提交数据库事务"]
    SAVE --> PENDING["登记新的待确认动作<br/>记录请求指标、延迟与日志"]
    PENDING --> FORMAT{"调用的是哪种接口？"}
    FORMAT -->|"/chat"| JSON["返回完整 JSON"]
    FORMAT -->|"/chat/stream"| SSE["此前已发送 started / node 进度<br/>此时发送最终答案的分段 token<br/>再发送 answer 与 done"]
    INVALID --> ERR["HTTP 应用错误响应<br/>SSE 开始后的异常受流状态限制"]
    JSON --> CLIENT["客户端展示答案、引用、策略和待确认动作"]
    SSE --> CLIENT
    CLIENT -. "用户确认后发起下一轮新请求" .-> U
```

参数校验失败、限流失败、未处理的节点异常等会中断正常流程，交由对应异常路径处理；图中没有为每一个处理框重复画异常箭头。SSE 已经开始发送后，不能假定仍可改成普通 JSON 错误响应。

必须分清图上的边与节点内部行为：

- DIRECT 会进入 `check_faithfulness` 节点，但该节点对 DIRECT 直接跳过模型检查。
- REFUSE 直接进入记忆节点，不经过生成与忠实度节点。
- 待确认动作依然经过 `execute_tools` 节点，但 Executor 当轮直接返回空结果，不执行计划。
- Graph 没有从忠实度节点返回检索节点的边。检索循环封装在 `SelfRAGLoop` 内部。
- Graph 没有从 Executor 返回 Planner 的循环，也没有配置节点级 checkpointer。

源码：`app/agents/graph.py`、`app/services/chat_service.py`、`app/agents/nodes/`。

## 4. 知识准备：文件怎样变成两套索引

“知识准备”是按职责划分的数据处理阶段；当前后端启动时也会直接运行它，并不一定是独立的离线服务。

```mermaid
flowchart TD
    FILE["knowledge/ 中支持格式的文件"] --> META["按文件名推导类目<br/>生成 document_id 与标题"]
    META --> PARSE{"Unstructured 启用且可用？"}
    PARSE -->|"是"| PART["解析元素：标题、正文、表格等<br/>按结构与重叠窗口形成 chunk"]
    PARSE -->|"否，或解析失败"| SUFFIX{"Markdown 文件？"}
    PART -->|"成功"| CLEAN["规范化文本、保存来源与章节等元数据<br/>生成稳定 chunk_id"]
    PART -->|"失败"| SUFFIX
    SUFFIX -->|"是"| MD["Markdown 标题切分 + 重叠窗口"]
    SUFFIX -->|"否"| SKIP["跳过该文件并记录日志"]
    MD --> CLEAN
    CLEAN --> PII["解析器返回的非 Markdown 片段可脱敏<br/>Markdown 政策正文保留"]
    PII --> DEDUP["精确去重<br/>近重复仅记录，不自动删除"]
    DEDUP --> EMB["对 chunk.content 生成 Embedding<br/>构建向量记录"]
    EMB --> BM["使用同批 chunks 构建内存 BM25"]
    EMB --> Q{"配置并成功写入 Qdrant？"}
    Q -->|"是"| QD[("Qdrant 向量索引")]
    Q -->|"否"| IM[("内存向量索引")]
    BM --> HY["HybridRetriever 使用两路索引"]
    QD --> HY
    IM --> HY
```

此图将不同解析路径共有的职责合并展示；清洗、切块与 ID 生成在具体函数中交织执行，不是三个独立网络服务。空知识库时跳过向量计算，仍可构建空索引。

源码：`app/retrieval/ingest.py`、`unstructured_parser.py`、`chunking.py`、`cleaning.py`、`app/providers/embeddings.py`。

## 5. 在线检索：SINGLE、MULTI 与 Hybrid 的关系

### 5.1 retrieve_docs 内部的策略分支

```mermaid
flowchart TD
    IN["user_query + strategy"] --> TYPE{"策略？"}
    TYPE -->|"SINGLE"| SR["改写问题<br/>原问题 + 改写去重后最多 2 条"]
    SR --> SH["逐条调用 HybridRetriever<br/>每条 top_k 默认 3"]
    SH --> SD["按 chunk_id 合并去重"]
    SD --> SC["按原问题做 Cross-Encoder 精排<br/>模型不可用则词法排序<br/>top_n 默认 5"]
    SC --> OUT["写入 retrieved_chunks<br/>供生成节点使用"]

    TYPE -->|"MULTI"| MR["SelfRAGLoop<br/>根据 missing_aspect 改写<br/>每轮原问题 + 改写最多 2 条"]
    MR --> MH["逐条调用 HybridRetriever<br/>每条 top_k 默认 8"]
    MH --> MD["轮内按 chunk_id 去重 → 精排<br/>将片段累积到跨轮结果"]
    MD --> GRADE["LLM 评估相关性与充分性<br/>输出 sufficient / missing_aspect 等"]
    GRADE --> CHECK{"充分，或已达轮数上限？"}
    CHECK -->|"是"| MO["返回累积结果<br/>上限为 rerank_top_n 的 2 倍"]
    CHECK -->|"否"| MISS["将缺失方面带入下一轮改写<br/>默认最多 3 轮"]
    MISS --> MR
    MO --> OUT
```

`SINGLE` 表示不进行证据充分性驱动的多轮循环，不表示只发出一次底层搜索。`MULTI` 评估器失败时，以“当前是否已有片段”作为充分性的回退判断，而不是强制继续搜索。

### 5.2 一次 HybridRetriever 调用

```mermaid
flowchart TD
    Q["一个 search_query + top_k"] --> CACHE{"检索缓存命中？"}
    CACHE -->|"是"| RETURN["返回 Hybrid 候选<br/>调用方仍可继续精排"]
    CACHE -->|"否 / 订单类查询绕过缓存"| BM["BM25.search<br/>捕获本路失败"]
    BM --> DENSE["query Embedding → VectorRetriever.search<br/>捕获本路失败"]
    DENSE --> EMPTY{"两路都没有候选？"}
    EMPTY -->|"是"| ERROR["抛出 RetrievalError"]
    EMPTY -->|"否"| RRF["RRF 按排名融合<br/>按片段标识合并，k 默认 60"]
    RRF --> TOP["截取 top_k → 写缓存"]
    TOP --> RETURN
```

源码中 BM25 和向量搜索是先后调用，两路故障被分别隔离；“双路召回”不等于已经使用异步并行。缓存保存的是 Hybrid 阶段结果，不是最终生成答案。

源码：`app/agents/nodes/retrieval.py`、`app/retrieval/query_rewrite.py`、`self_rag.py`、`hybrid.py`、`fusion.py`、`cache.py`、`reranker.py`。

## 6. 工具分支：规划、确认、执行与数据访问

```mermaid
flowchart TD
    IN["AGENT 分支"] --> CONF{"已有有效 confirmed_action？"}
    CONF -->|"是"| FIXED["使用服务端保存的工具名和参数<br/>直接构造单步计划，不重新让模型决定动作"]
    CONF -->|"否"| SKILL["按触发词或意图匹配 Skill<br/>收窄工具目录并提供流程说明"]
    SKILL --> LLM["Planner 调用 LLM 生成 AgentPlan JSON<br/>解析失败回退到 Skill 计划或知识检索"]
    LLM --> SAN["模型计划过滤未知或不允许的工具<br/>最多保留 6 步"]
    SAN --> WRITE["识别写操作，校验是否明确请求执行<br/>缺订单号则返回补充信息提示<br/>非明确写请求过滤相应写步骤"]
    WRITE --> WAIT{"剩余计划有未确认写操作？"}
    WAIT -->|"是"| PROPOSE["生成 pending_action<br/>Executor 当轮不执行整个计划<br/>Generate 返回确认文案"]
    PROPOSE --> SERVICE["ChatService 将提案保存在进程内<br/>绑定 session_id / user_id，15 分钟有效"]
    SERVICE -. "客户端下一轮携带 confirm_action_id" .-> NEW["重新进入完整请求入口<br/>ChatService 核验并恢复动作"]
    NEW -. "经 Graph 路由后" .-> FIXED
    WAIT -->|"否"| EXEC["Executor 按计划顺序执行<br/>受工具调用次数与步数上限约束"]
    FIXED --> EXEC
    EXEC --> RISK{"工具风险类型？"}
    RISK -->|"WRITE / DESTRUCTIVE"| PERM["确认权限校验<br/>幂等键 + 工具及参数指纹"]
    PERM --> IDEM{"幂等记录？"}
    IDEM -->|"相同键与指纹"| REUSE["复用已有结果"]
    IDEM -->|"键相同、指纹不同"| CONFLICT["记录幂等冲突为失败 ToolResult"]
    IDEM -->|"未命中"| RUNWRITE["Tool.run 参数 Schema 校验<br/>业务仓储检查订单归属及业务条件<br/>执行写入并记录幂等结果"]
    RISK -->|"其余类型"| RUNREAD["Tool.run 参数校验并执行<br/>映射中的只读工具失败可走固定回退表"]
    RUNWRITE --> RESULT["收集 ToolResult<br/>成功输出或失败原因 → 生成节点"]
    RUNREAD --> RESULT
    REUSE --> RESULT
    CONFLICT --> RESULT
```

工具的具体依赖如下：

| 工具类型 | 实际依赖 |
|---|---|
| 订单、商品、物流、退换货与退款等业务工具 | 请求级 SQLAlchemy Session、仓储、演示业务数据库；不是已接入真实支付或承运商 |
| `search_knowledge` | HybridRetriever；不等于重新进入完整的 Graph 检索节点与多轮精排流程 |
| 本地 MCP 风格工具 | `app/mcp/runtime.py` 中的本地处理器 |
| 可配置的远端工具适配 | HTTP POST 到配置端点，传递工具名与参数 |

ToolRegistry 可以导出 OpenAI 风格 Function Calling Schema；当前 Planner 主路径是“工具目录文字 + 结构化 AgentPlan JSON”，不是直接把 `openai_tools()` 传给模型并依靠模型的原生 tool_calls 循环。

MCP 部分是本地代理与简化 HTTP 适配；不能从这个架构推断已经实现完整 MCP 标准客户端的协商、发现与会话生命周期。

源码：`app/agents/nodes/planner.py`、`executor.py`、`app/tools/{base,registry,factory,permissions}.py`、`app/skills/loader.py`、`app/mcp/{adapter,runtime}.py`、`app/repositories/`。

## 7. 生成、忠实度、记忆与返回

### 7.1 生成与忠实度处理

```mermaid
flowchart TD
    IN["generate_answer"] --> SPECIAL{"需要特殊回复？"}
    SPECIAL -->|"工具全失败 / 缺订单号 / 待确认"| FIXED["返回固定失败提示、补参数提示或确认文案"]
    SPECIAL -->|"普通回答"| GEN["原问题 + 意图 + 策略<br/>前 6 条检索证据 + 工具结果<br/>调用模型或离线回答；生成失败用抽取式兜底"]
    GEN --> CIT["将模型给出的 chunk_id 映射为 Citation"]
    FIXED --> CHECK["check_faithfulness"]
    CIT --> CHECK
    CHECK --> SKIP{"拒答、待确认、缺订单号<br/>离线 Provider 或 DIRECT？"}
    SKIP -->|"是"| MEM["进入 compact_memory"]
    SKIP -->|"否"| EMPTY{"SINGLE / MULTI 却没有片段？"}
    EMPTY -->|"是"| REF["改为证据不足拒答，清空引用"]
    EMPTY -->|"否"| JUDGE["模型判断答案是否受证据支持"]
    JUDGE -->|"支持"| MEM
    JUDGE -->|"检查器不可用"| OFF["用离线模板或抽取方式构造降级回答"]
    JUDGE -->|"不支持"| REWRITE["基于原有证据重写一次并复核"]
    REWRITE -->|"支持"| MEM
    REWRITE -->|"失败或仍不支持"| EXTRACT["抽取式兜底并复核"]
    EXTRACT -->|"支持"| MEM
    EXTRACT -->|"仍不支持"| REF
    OFF --> MEM
    REF --> MEM
```

这里没有重新检索。`check_faithfulness` 是模型辅助判断，不构成绝对事实保证。当前生成 Prompt 未直接注入会话历史或摘要；它主要消费本轮问题、检索证据和工具结果。

### 7.2 记忆节点的实际位置与处理

记忆节点位于本轮生成之后。它先将本轮用户和助手消息加入内存状态，再根据“消息 + 摘要”的字符近似 Token 数决定等级；当前判级没有计算检索片段、工具结果和整份模型 Prompt 的总长度。

| 默认利用率 | 实际处理 |
|---|---|
| 低于 50% | 不进入分级压缩；工具结果仍有 10000 字符上限 |
| 50% 至不足 70% | 工具输出超长时缩为 400 字符预览 |
| 70% 至不足 85% | 工具预览缩为 160 字符；历史窗口保留最近约四轮 |
| 大于等于 85% | 在上述截窗之后生成摘要，再应用压缩；摘要失败有文本拼接回退 |

`ChatService` 会保存本轮原始用户消息和最终助手回答，以及非空摘要；不会用压缩后的窗口替换数据库的全部历史消息。当前 `_initial_state` 读取最近 20 条消息，却把 `summary` 初始化为空，没有把已保存摘要重新装入下一轮状态。这是现有链路的限制，不能将图理解为已经完成长期记忆闭环。

源码：`app/agents/nodes/memory.py`、`app/memory/{budget,compression,summarizer}.py`、`app/services/chat_service.py`、`app/repositories/session_repository.py`。

### 7.3 JSON 与 SSE 的返回区别

```mermaid
sequenceDiagram
    participant C as 客户端
    participant A as FastAPI
    participant S as ChatService
    participant G as LangGraph
    participant D as 数据库
    C->>A: POST /api/v1/chat/stream
    A->>S: stream(ChatRequest)
    S->>D: 请求级会话、确认核验后的历史读取
    S-->>C: started
    S->>G: astream，stream_mode 为 updates
    loop 每个节点完成
        G-->>S: 节点状态更新
        S-->>C: node，部分事件附意图或策略
    end
    Note over S,G: 完成本轮生成、适用的忠实度处理与记忆处理
    S->>D: 保存消息与非空摘要，commit
    Note over S: 保存新提案，记录指标
    S-->>C: token：将最终答案每 48 字符分段
    S-->>C: answer：完整 ChatResponse
    S-->>C: done
```

这是正常完成路径。非流式 `/chat` 使用 `ainvoke`，不发送这些进度事件，完成后返回完整响应。当前聊天 SSE 没有将模型原始生成 token 实时透传给客户端；因此不能把 Provider 自带的流式能力直接等同于产品端已使用它。

## 8. 状态与资源：什么随请求走，什么被复用

| 类别 | 内容 | 生命周期或位置 |
|---|---|---|
| 请求身份字段 | `trace_id`、`session_id`、`user_id`、`user_query` | 本轮 AgentState |
| 决策结果 | `intent`、`complexity`、`strategy` | 节点产生并更新 State |
| 检索数据 | `rewritten_queries`、`retrieved_chunks` | 检索节点产生，供本轮后续使用 |
| 工具数据 | `plan`、`tool_results`、`pending_action`、`confirmed_action` | 规划与执行节点使用 |
| 回答数据 | `final_answer`、`citations`、`refused`、`error` | 生成、拒答或忠实度节点更新 |
| 记忆及观测 | `messages`、`summary`、`latency`、`token_usage`、`extra` | State 内的业务数据 |
| 请求级 DB Session | SQLAlchemy AsyncSession | 通过 contextvars 供仓储型工具取得；不放入 State |
| 编译后的 Graph、工具注册表、Provider、检索器 | 可复用组件 | 容器或 ChatService 持有，跨请求复用 |
| 待确认动作表 | 动作参数、用户、会话、过期时间 | ChatService 进程内字典，不是数据库或 Redis |
| 已持久化记录 | 消息、摘要、订单、退款、审计与幂等等 | SQL 数据库；不同记录由对应仓储操作 |

节点返回局部状态更新；`AgentState` 没有无限追加消息的 reducer。会话消息持久化也不等于 Graph 节点级断点续跑。

## 9. 降级、观测与运维入口

| 场景 | 当前实现 |
|---|---|
| 数据库不可用 | 启动初始化失败或运行时出错；不自动换数据库。`ready` 的整体判定只把数据库作为硬依赖 |
| Redis 启动不可用 | 选择内存检索缓存与内存限流 |
| Redis 运行时限流出错 | 放行本次请求；不是自动切换到内存限流 |
| Redis 运行时缓存读写出错 | 缓存读视为未命中、写失败忽略；继续实际检索 |
| 配置的 Qdrant 建库或写入失败 | 启动入库降级为内存向量存储；不能推断所有运行时故障也会自动迁移 |
| 未配置 LLM | 使用 OfflineLLMProvider |
| LLM 暂时性请求错误 | Provider 对可重试错误使用指数退避和抖动；耗尽后各调用模块分别回退 |
| 本地 Embedding 加载不可用 | 构建时选择 hash；远端 Embedding API 报错不代表有通用的自动本地切换链 |
| Cross-Encoder 模型不可用 | 词法排序；不是 Cohere，也不能冒充 Cross-Encoder 成绩 |
| BM25 或向量单路失败 | 保留另一条路的候选做融合；两路都无结果抛错 |
| 只读工具失败 | 部分工具可按固定表回退；权限拒绝不进入回退，写操作没有替代写动作的回退 |
| 生成或忠实度失败 | 见第 7 节的抽取、离线模板、重写与拒答路径 |

| 运维接口 | 用途 |
|---|---|
| `/api/v1/health` | 存活状态 |
| `/api/v1/ready` | 检查数据库等依赖，报告依赖状态 |
| `/api/v1/capabilities` | 报告后端选择及降级信息；部分字段按配置推导，不等于全链路实测 |
| `/api/v1/admin/tools`、`/api/v1/admin/skills` | 查看工具与技能；管理接口使用单独的管理令牌规则 |
| `/metrics` | Prometheus 指标导出 |

路径前缀按默认 `/api/v1` 展示，可由 Settings 配置。日志与指标分布在请求入口、服务、检索和工具等模块，不是所有请求结束后才启动的单独处理服务。当前 `token_usage` 不是对意图、改写、规划、判别等全部模型调用的完整成本汇总。

## 10. 对原架构图与面试表述的校正

| 容易形成的理解 | 按当前源码应怎样理解 |
|---|---|
| 系统架构就是五条策略分支 | 五分支是 Graph 内部的控制流；外面还有接入、会话、装配、存储与返回 |
| 每个框代表独立服务或独立 Agent | 大部分是同一 Python 应用中的模块；当前没有多 Agent 团队协作 |
| 护栏节点检查所有业务边界 | 当前该节点直接调用注入检测；越界还由意图和路由处理。`boundary.py` 存在，但没有接入当前主请求链 |
| 按 0.4 / 0.7 分数阈值选策略 | 当前是模型结构化分类与规则回退，没有这组显式阈值分支 |
| SINGLE 只有一次搜索 | 可同时使用原问题和一条改写，各调用一次 Hybrid；没有充分性驱动的补检循环 |
| 忠实度失败沿 Graph 回边重查知识库 | 实际在节点内部重写或抽取；检索补证据循环位于 SelfRAGLoop |
| 确认后从中断的 Graph 节点继续 | 确认是下一轮新请求，经校验后使用保存的动作重新进入 AGENT 分支 |
| 持久化会话等于长期记忆闭环 | 当前摘要回读、历史注入生成等尚未闭环，见第 7 节 |
| Schema 校验和 user_id 隔离等于身份认证 | 聊天 API 当前直接接受请求体 user_id，不能视为已有可信用户认证 |
| SSE 就是边生成边展示模型 token | 当前先发节点进度，最终答案处理完成后按字符分段发送 |
| 本地/HTTP MCP 适配等于完整 MCP 客户端 | 当前主要是统一工具接口与简化传输，需按实现边界描述 |

阅读时可以用一句话串起全图：客户端提交请求，FastAPI 接入并校验，ChatService 管理本轮生命周期，LangGraph 选择并执行处理路径，检索与工具提供证据或业务结果，适用的忠实度与记忆处理完成后，由 ChatService 持久化并返回。
